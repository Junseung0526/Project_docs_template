## 2. 설계 원칙

<!-- 팀이 의견 충돌할 때 판단 기준이 되는 원칙 3~5개. 위에 있을수록 우선. -->

| # | 원칙 | 의미 | 적용 예 |
| :---: | :--- | :--- | :--- |
| 1 | **보안 우선** | 민감 정보는 암호화 저장, 화면에는 마스킹 | 비밀번호 해시, 전화번호 마스킹 |

## 3. 사용자와 권한

```mermaid
flowchart LR
    subgraph U["사용자"]
        A["관리자"]
        B["일반 사용자"]
        C["비회원"]
    end
    subgraph S["접근 범위"]
        A1["전체 데이터 조회·관리"]
        B1["자기 데이터 생성·수정"]
        C1["공개 화면만 열람"]
    end
    A --> A1
    B --> B1
    C --> C1
    A1 -. 포함 .-> B1
```

| 역할 | 할 수 있는 일 | 할 수 없는 일 |
| :--- | :--- | :--- |
| **관리자** | 전체 조회, 권한 부여, 설정 관리 | — |
| **일반 사용자** | 자기 데이터 생성·수정·삭제 | 다른 사용자 데이터 접근 (서버에서 403) |
| **비회원** | 공개 화면 열람 | 쓰기 작업 전부 |

## 6. 데이터 모델

```mermaid
erDiagram
    USER ||--o{ ITEM : "소유"
    ITEM ||--o{ ITEM_LOG : "변경 이력"

    USER {
        uuid id PK
        string email "이메일"
        string role "관리자/일반"
        timestamp created_at "가입 일시"
    }
    ITEM {
        uuid id PK
        uuid user_id FK
        string title "제목"
        string status "작성중/완료"
    }
    ITEM_LOG {
        uuid id PK
        uuid item_id FK
        string action "생성/수정/삭제"
        timestamp created_at "일시"
    }
```

| 도메인 | 핵심 엔티티 | 메모 |
| :--- | :--- | :--- |
| 사용자 | `USER` | 역할로 권한 구분 |
| 업무 | `ITEM` | 프로젝트의 핵심 데이터로 이름을 바꾸세요 |
| 이력 | `ITEM_LOG` | 누가 언제 무엇을 바꿨는지 |

## 8. 보안 및 데이터 관리

| 영역 | 규칙 |
| :--- | :--- |
| 접근 제어 | 역할·소유 범위를 **서버에서** 검사. 범위 밖 요청은 403 |
| 민감 정보 | 비밀번호는 해시, 키·토큰은 환경 변수로 코드와 분리 |
| 감사 로그 | 중요한 수정에 수정자·일시·변경 전/후 값 기록 |
| 개발 | 실제 개인정보는 저장소에 올리지 않음. 테스트는 가짜 데이터 |
